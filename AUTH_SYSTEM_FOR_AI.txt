4. SERVER.JS ARCHITECTURE
================================================================================

Middleware (in order):
1. express.urlencoded + express.json
2. express-session (24h cookie, httpOnly, sameSite: lax)
3. connect-flash
4. helmet (CSP and COEP disabled)
5. cors
6. express.static public + uploads
7. Custom: inject locals (req.db, user, messages, currentLang, csrfToken)
8. Custom: CSRF guard (skips multipart)

Route mounting:
- /auth      -> routes/auth.js       (authLimiter: 50/15min POST-only)
- /student   -> routes/student.js    (generalLimiter: 200/15min POST-only)
- /admin     -> routes/admin.js      (generalLimiter: 200/15min POST-only)
- /committee -> routes/committee.js  (generalLimiter: 200/15min POST-only)
- GET /      -> inline (queries majors, categories, scholarshipTypes, provinces)

Error handling: 404 handler, global error handler, trust proxy: 1

11. FLOW SUMMARY
================================================================================

1. REGISTRATION:
   User fills form -> check settings (registration_open/start/end) ->
   check duplicates -> bcrypt.hash(password, 12) ->
   IF email: INSERT with verification_token -> send email link
   IF telegram: INSERT unverified -> send OTP via Telegram API -> redirect to verify-otp

2. VERIFICATION:
   Email: Click link -> /auth/verify-email/:token -> UPDATE is_verified=1
   Telegram: Enter code -> /auth/verify-otp -> telegramOtp.verifyOTP() -> UPDATE is_verified=1

3. LOGIN:
   Find by email/username/phone -> bcrypt.compare ->
   Check is_verified -> store session -> redirect by role

4. SCHOLARSHIP APPLICATION:
   Student fills form (personal, contact, family, education, document uploads) ->
   check registration+scholarship windows -> upload to ImageKit -> status=pending ->
   Admin reviews -> under_review -> approved/rejected/correction_requested ->
   Email notification at each status change

5. ENROLLMENT:
   Student fills form (academic, personal, family, documents) ->
   check enrollment window -> check duplicate per year+semester ->
   upload docs to ImageKit -> status=pending -> Admin approves/rejects

6. PAYMENT (Bakong KHQR):
   Student views tuition page -> system calculates:
     discount = tuition_per_year * coverage_percentage / 100
     studentPays = tuition_per_year - discount + ministry_fee
   Student generates QR -> system calls generateKHQR() -> stores khqr_md5+khqr_string
   Student scans QR with banking app -> system polls check-transaction/:md5
   On success: payment auto-verified -> receipt page
   Fallback: manual payment with proof upload -> admin verifies

7. ADMIN MANAGEMENT:
   Applications: review, approve (with exam details), reject, request correction
   Enrollments: approve/reject with notes
   Payments: verify/reject with admin tracking
   Reports: statistics + Excel/PDF export
   Settings: control registration/enrollment/scholarship windows

8. COMMITTEE:
   Read-only access to approved applications and reports
