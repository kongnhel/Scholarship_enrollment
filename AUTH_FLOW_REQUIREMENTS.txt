================================================================================
SYSTEM REQUIREMENTS - Scholarship & Enroll Online (NMU)
================================================================================
This document describes the complete system flow and behavior.
Tech Stack: Node.js, Express.js, EJS templates, MySQL, Tailwind CSS
Institution: National Meanchey University (NMU), Cambodia

Last Updated: September 2026

================================================================================
GENERAL
================================================================================

- 3 user roles: student, admin, committee
- All passwords hashed with bcrypt (12 rounds)
- Session-based authentication (cookie, 24 hours expiry)
- CSRF protection on all POST/PUT/DELETE/PATCH forms (skips multipart)
- Rate limiting: auth routes (50 req/15min), general routes (200 req/15min)
- Registration/enrollment/scholarship windows controlled by admin via settings table
- Flash messages for success/error feedback (redirect-based, shown as SweetAlert2)
- Bilingual support (Khmer + English) on all pages via ?lang= query param
- Dark mode with localStorage persistence and system preference fallback
- File storage via ImageKit cloud service
- Email via Resend API (primary) or SMTP nodemailer (fallback)

================================================================================
1. AUTHENTICATION SYSTEM
================================================================================

--- LOGIN ---

- Single login field accepts email, username, OR phone number
- System looks up user WHERE email = ? OR username = ? OR phone = ?
- Compare password with bcrypt
- If password wrong: show "Invalid credentials"
- If user is not verified (is_verified = 0): redirect to /auth/verify-otp
- If verified: store user info in session (id, email, phone, role, names, username, profile_pic)
- Redirect based on role: admin -> /admin/dashboard, committee -> /committee/dashboard, student -> /student/dashboard

--- REGISTRATION ---

- Fields: Khmer name, English name, username, email, phone, password, confirm password, verification method
- Username: 3-50 characters, letters/numbers/underscore only, must be unique
- Email: valid format, must be unique
- Phone: must be unique
- Password: minimum 6 characters, must match confirm password
- User chooses verification method: Email OR Telegram

Before registering:
1. Check if registration is open (settings.registration_open)
2. Check if current date is within registration_start and registration_end
3. Check for duplicate username, email, and phone

After validation:
1. Hash password with bcrypt (12 rounds)
2. Insert user with is_verified = 0
3. Send verification based on chosen method

--- VERIFICATION METHOD: EMAIL ---

1. Generate UUID token, store with 1-hour expiry (verification_token, token_expires_at)
2. Send email with verification link: /auth/verify-email/:token
3. User clicks link -> set is_verified = 1, clear token
4. Resend: new token generated, new email sent

--- VERIFICATION METHOD: TELEGRAM ---

1. After registration, redirect to /auth/verify-otp page
2. System sends Telegram login code via TelegramClient API (auth.SendCode)
3. User enters 5-digit code on verification page
4. System verifies via TelegramClient API (auth.SignIn)
5. If correct: set is_verified = 1
6. Max 5 attempts before code invalidated

--- OTP VERIFICATION (shared) ---

- 5-digit numeric code
- Stored in users table: otp_code, otp_expires_at, otp_attempts, otp_last_sent_at
- Default expiry: 10 minutes (OTP_EXPIRY_MINUTES env)
- Max attempts: 5 (OTP_MAX_ATTEMPTS env)
- Resend cooldown: 60 seconds (OTP_RESEND_COOLDOWN env)
- Page shows masked phone number (e.g., +85512***456)

--- FORGOT PASSWORD ---

1. User enters email on /auth/forgot-password
2. Generate UUID token, store with 1-hour expiry (reset_token, reset_token_expires)
3. Send email with reset link: /auth/reset-password/:token
4. Always show same message regardless of email existence (prevents email enumeration)

--- PROFILE ---

- View profile: shows profile picture, names, role, username, email, phone
- Edit profile: update khmer_name, english_name, email, phone, profile picture (ImageKit)
- Change password: requires current password verification first
- Username is readonly

================================================================================
2. SCHOLARSHIP APPLICATION SYSTEM (Student)
================================================================================

--- NEW APPLICATION (POST /student/application) ---

Form fields:
- Personal: khmer_first_name, khmer_last_name, english_first_name, english_last_name, gender, date_of_birth, nationality
- Contact: current_address, phone, telegram, email
- Family: parent_name, parent_phone, emergency_contact, emergency_phone
- Education: school_name, school_province_id, graduation_year, exam_result
- Choices: major_first_choice_id, major_second_choice_id, scholarship_category_id, scholarship_type_id
- Documents: photo, transcript, additional_documents (up to 5)

Logic:
1. Check registration AND scholarship windows are open
2. Upload 3 file types to ImageKit (photo, transcript, additionalDocs)
3. Handle nationality_other custom value
4. Set status = 'pending'
5. Record initial status in application_status_history
6. Send confirmation email

--- APPLICATION STATUS FLOW ---

pending -> under_review -> approved/rejected/correction_requested
correction_requested -> pending (after student corrects and resubmits)

--- CORRECT APPLICATION (POST /student/application/:id/correct) ---

- Only allowed when status = 'correction_requested'
- Re-uploads files to ImageKit (preserves old files if new ones not provided)
- Resets status to 'pending'
- Records status history

3. ENROLLMENT SYSTEM (Student)
================================================================================

--- ENROLLMENT FORM (GET /student/enroll) ---

Loads:
- User profile data
- Latest application (if any)
- Existing enrollment for current academic year
- Fee types (active)
- Payment history
- Majors and tuition fees
- Scholarship types with coverage info
- Settings (enrollment open/close)

--- SUBMIT ENROLLMENT (POST /student/enroll) ---

Form fields:
- Academic: academic_year (hardcoded '2026-2027'), semester ('1'), major_choice
- Personal: khmer/english names, gender, date_of_birth, place_of_birth, village, phone, current_address
- Address: province, district, commune
- Family: father_name, mother_name, parent_name, parent_phone, parent_relationship, occupation, education_level, guardian_phone
- Education: previous_school, previous_diploma, diploma_year
- Documents: doc_transcript_file, doc_birth_cert_file, doc_photo_4x6_file, doc_photo_3x4_file
- Signature dates: student_signature_date, parent_signature_date

Logic:
1. Check enrollment window is open
2. Check duplicate enrollment per academic_year + semester
3. Upload 4 document files to ImageKit
4. Set status = 'pending'
5. Redirect to success page

--- TUITION LOOKUP (GET /student/enroll/tuition/:majorId) ---

- AJAX endpoint returning JSON
- Queries major_tuition table for the major's latest active tuition
- Returns {success, tuition} for dynamic fee display

================================================================================
4. PAYMENT SYSTEM (Student)
================================================================================

--- PAYMENT PAGE (GET /student/payments) ---

Loads:
- Enrollment record
- Payment history
- Fee types
- Total paid (sum of verified payments)
- Tuition info from major_tuition
- Scholarship discount info from scholarship_types
- QR code image path from settings

--- TUITION CALCULATION FORMULA ---

discount = tuition_per_year * coverage_percentage / 100
studentPays = tuition_per_year - discount + ministry_fee

Where:
- tuition_per_year comes from major_tuition table
- coverage_percentage comes from scholarship_types table
- ministry_fee comes from scholarship_types table

--- HOW PAYMENT ACTUALLY WORKS (there is no QR generation) ---

The Bakong KHQR integration was removed. Students do not generate a QR code. Instead:

  Admin uploads a bank QR image in /admin/settings -> saved in the `payment_qr_path`
      setting (an ImageKit URL).
  Student opens /student/payments -> the page renders that uploaded image.
  Student scans it with their banking app and pays.
  Student submits a payment SCREENSHOT to /student/payments (proof + transaction ref).
  Admin verifies or rejects it from /admin/payments.

The khqr_md5 / khqr_string columns still exist on older databases but nothing reads them.

--- MANUAL PAYMENT (POST /student/payments) ---

1. CSRF check
2. Reject if no enrollment_id given
3. Verify the enrollment belongs to the logged-in student (ownership check)
4. Derive the amount server-side from major_tuition + scholarship coverage via
   computeTuitionDue(); the browser-supplied `amount` is ignored entirely
5. pay_period accepted only as 'year' | 'semester'; amount is recomputed, never trusted
6. Reject a duplicate pending payment for the same enrollment + amount
7. Upload proof image to ImageKit
8. Insert payment with payment_method='bank_transfer', status='pending'
9. Admin manually verifies later

--- PAYMENT STATUSES ---

pending -> verified (by admin)
pending -> rejected (by admin, with a reason recorded in admin_notes)

--- PAYMENT METHODS ---

bank_transfer (default), aba, acleda, wing, cash

5. ADMIN DASHBOARD
================================================================================

--- APPLICATION MANAGEMENT ---

- List all applications with pagination and filters (status, major, category, province, gender, date range)
- View application detail with full info and status history
- Actions: Mark Under Review, Approve (with exam details), Reject (with reason), Request Correction
- Each action: updates status, records history, creates notification, sends email

--- ENROLLMENT MANAGEMENT ---

- List all enrollments with payment stats (verified count, total paid)
- View enrollment detail with payment history
- Actions: Approve, Reject (with admin notes)

--- PAYMENT MANAGEMENT ---

- List all payments with search and status filter
- Shows total verified amount
- Actions: Verify, Reject (with admin notes and verified_by tracking)

--- MAJOR MANAGEMENT ---

- CRUD operations (add, edit, toggle active/inactive, delete)
- Search by name/faculty, pagination

--- SCHOLARSHIP TYPE MANAGEMENT ---

- CRUD with coverage_percentage, duration_years, provider_name, ministry_fee
- Toggle active/inactive, search, pagination

--- FEE TYPE MANAGEMENT ---

- CRUD with name (bilingual), amount, description
- Toggle active/inactive

--- MAJOR TUITION MANAGEMENT ---

- Per-major tuition fees by academic year
- CRUD with duplicate check (major_id + academic_year)
- Toggle active/inactive

--- PROVINCE MANAGEMENT ---

- CRUD with bilingual names

--- USER MANAGEMENT ---

- List users with role filter and search
- Admin can reset user password (generates random 8-char, flashes new password)
- Admin cannot delete other admin users

--- SYSTEM SETTINGS ---

9 configurable settings:
- registration_open, registration_start, registration_end
- enrollment_open, enrollment_start, enrollment_end
- scholarship_open, scholarship_start, scholarship_end
- payment_qr_file (QR code image upload)

--- REPORTS AND EXPORT ---

- Statistics: by major, by category, by province, by gender, by status
- Export to Excel (exceljs) and PDF (pdfkit)
- Send exam notifications to all approved applications

================================================================================
10. SECURITY NOTES
================================================================================

- Passwords hashed with bcrypt, 12 salt rounds
- CSRF token required on all state-changing requests (except file uploads)
- Rate limiting on auth routes to prevent brute force
- OTP max attempts prevents unlimited guessing
- OTP resend cooldown prevents spam
- Registration/enrollment/scholarship open/close dates enforced
- Token expiry on email verification and password reset (1 hour)
- File upload limited to 5MB, specific MIME types only
- Helmet.js headers enabled (CSP and cross-origin disabled)
- Session cookie: httpOnly, sameSite: lax, maxAge: 24 hours
- trust proxy: 1 for IIS reverse proxy support
